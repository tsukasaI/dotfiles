# Claude Code 利用とハーネスの評価フレームワーク

決定日: 2026-11-15（/grill セッションで合意し、同日に Fable のレビューを受けて改訂）。対象は自分が所有するリポジトリ全体での Claude Code の使い方と、それを支えるハーネス（`claude-code/` 配下の設定、shguard、hooks、skills）。

背景: 2026-10-15〜11-15 の dotfiles 170 コミットのうち 106 件が `claude-code/` への変更だった。変更は感覚で、気になったときに入れており、効果を確かめていなかった。週間リミットの残量を見て、作業を詰め込むこともあった。

## 0. 頂点の目的

- AI を使うこと自体を目的にしない。使用枠を使い切ることも目的にしない。
- 目的は次の2つ。
  - AI をうまく設計して人間の時間を空け、その時間をより高い次元の作業（仕様や PM 領域、深い技術の習得、キャリアの準備）に回す。
  - その設計を、話すことや書くことで外に価値として出す。
- 空いた時間がどこに使われたかは測らない。月次見直しで1行だけ自己申告する。
- 使用枠が余っているときは、ハーネスをいじるのではなく、ops に置いたキャリアとプロダクトの Issue キューから作業を取る。何もしないことも許容する。

## 1. 優先順位

キャリア > 個人プロダクトの出荷 > 技術力 > 運用の自動化。目的同士が衝突したときは、この順で決める。技術力は測らない。

## 2. 成果の軸と品質

| 軸 | 定義 | データ源 |
|---|---|---|
| キャリア | 外部で使われたネタ（業務での採用、OSS への貢献、登壇、執筆、外部の場で語れたこと） | ops のネタ帳。月次見直しで候補を提案し、採否は本人が決める |
| 出荷 | PR があるリポジトリはマージ PR、main 直コミットのリポジトリは `feat`/`fix` コミット（`chore`/`docs` は除く）。プロダクト系とハーネス系（dotfiles）は分けて集計する | git log、`gh pr list` |
| 自律稼働 | 計画の承認後からマージまで、ユーザー発言（システム通知を除く）がなかったセッション | transcript |
| 品質（手戻り率） | マージ後の `fix` コミットと、レビューの往復回数。前月比の傾向だけを見る | git log、`gh pr view` |

- 外への価値（発信）はキャリア軸に含める。「価値があった」と言えるのは、誰かが真似した、外部の場で語れた、業務で使えた、のいずれかが起きたとき。件数ではなく、起きた事実として記録する。反応の数は追わない（LT はもともと反応が少ない）。
- 3か月続けて発信がゼロなら、月次見直しで1行だけ指摘する。目標値にはしない。
- ハーネス作業が成果として数えられるのは、外に出る成果物（LT、記事）に紐づいたときだけ。「ネタになるから」は、どのハーネス変更にも後付けできてしまうため。
- 使用量: 余った枠は損失ではない。ステータスラインが受け取る `rate_limits`（5時間枠と7日枠の消費率）と `cost.total_cost_usd` は、上限に当たって作業が止まっていないかを見るためだけに記録する。成果あたりの使用量は評価しない。

## 3. 介入の分類

- **必要な介入**: 取り返しのつかない破壊的操作、外向きの操作、設計判断。git で戻せる操作（追跡済みファイルの削除など）はここに入れない。件数は観察だけする。ゼロになったら危険信号として扱う。
- **不要な介入**: 安全なコマンドをユーザーに手渡したもの、許可済みのことへの確認、異常停止からの再開。減る向きを見る。
- hook の拒否と、手渡しは別物として扱う。拒否されても Claude が別の手段で進めることは多いので、数えるのは実際にユーザーへ手渡したコマンドだけにする。
- 数値目標は置かない。介入率を下げること自体を目標にすると、指標がハックされるため。
- 集計の仕方:
  - 決定的に数えられるもの（手渡し、異常停止、システム通知を除くユーザー発言）は、スクリプトで別々に数える。
  - 判断が要る分類は、月次でランダムに抜き出した 5 セッションを本人が分類する。
  - 拒否されたコマンドの傾向は軽量モデル（`haiku`/`sonnet`）にまとめさせる。Claude による全件分類はしない。
- 許可ルールは自動では追加しない。月次で Claude が案を出し、本人が1件ずつ承認し、`hooks-guardrails` の手順で反映する。AI が自分の権限を自分で広げる経路は作らない。
- 理解の確認はゲートにしない（自律性を損なうため）。代わりに月次見直しの固定項目として、マージ済みの PR を1件選んで自分で説明できるかを5分で確かめる。

## 4. 見張り役（失敗シグナル）

- **安全性の後退**: ガードファイル（dotfiles の `claude-code/shguard/`、`claude-code/settings.json`、`claude-code/hooks/`、および shguard リポジトリ）を触るコミットを、月次の表に全件並べる。緩和かどうかは差分から機械的に判定できないため、全件に仮説 Issue への参照を必須にする。参照のないコミットは、それ自体を失敗として扱う。
- **見かけだけの改善**: 緊急トリガーの件数を、ラベル `harness-urgent` の付いた Issue の数で月ごとに並べる。不要な介入が減っているのに緊急トリガーが減っていなければ、ハックの兆候とみなす。
- **目的化**: ハーネス系のコミット（dotfiles の `claude-code/`、shguard）が、7日枠の残量が多い時期に集中していないかを、記録した `rate_limits` と突き合わせて検出する。
- **運用の停止**: 月次見直しが2回続けて行われなければ、枠組みが回っていないとみなす。
- 枠組み自体の見直しは3か月後に行う。不要な介入も緊急トリガーも改善していなければ作り直す。月の作業量が極端に少ない場合は、6か月に延ばす。

## 5. 変更の採否ルール

- ハーネスに変更を入れる前に、仮説 Issue を dotfiles に1件立てる（ラベル `harness-hypothesis`）。本文には仮説、判定に使う指標、見直し日、種別（通常か安全系か）を書く。dotfiles は public なので、書くのは集計値と仮説だけにする。セッションの中身や private リポジトリの名前は書かない。
- 変更の一覧は、git log の差分パスから自動で拾う。コミットメッセージには仮説を書かない（ガードファイルの Issue 参照は例外）。
- 見直し日に指標がはっきり動いていなければ、1回だけ延長する。2か月たっても動かなければ、既定で元に戻す。効果のない指示は、使用量だけを増やして残るため。ETH Zurich の AGENTS.md 評価では、コンテキストファイルが成功率を全般的には改善せず、推論コストを 20% 超増やした。
- 安全系の変更（破壊的操作の遮断など）は「効果がなければ戻す」の対象外にする。効いているほど何も起きないので、指標が動かないため。

## 6. 見直しの手順

- **月次（チェックリスト）**:
  1. 本人が集計スクリプトをローカルで実行する（この Mac の `logs.db` を読むため、ローカルでしか動かない）。
  2. スクリプトが数値表を出す。各軸、手渡しの上位、見直し日を迎えた仮説、見張り役の4項目が入る。
  3. 軽量モデルが拒否の傾向をまとめ、5 セッションのサンプルを提示する。
  4. 本人が各仮説を判定する（継続・延長・戻す）。
  5. 許可ルールの案を1件ずつ承認または却下する。
  6. 理解確認を1件行う。
  7. ネタの候補を提案する。
  8. 空いた時間の行き先を1行で自己申告する。
  9. 結果を記録する。

  /retro（ops の週次）とは別にする。
- **緊急**: トリガーは、同じ失敗が2回目に起きたとき、データ損失やセキュリティの問題、hook が正当な作業を止めたときの3つ。トリガーごとに `harness-urgent` ラベルの Issue を立てる。
  - セキュリティとデータ損失だけはその場で直す。
  - それ以外は、その場では本人がコマンドを実行して作業を続け、仮説 Issue を立てて月次で直す。
  - 同じ拒否が1週間に3回以上出たら、月次を待たずに前倒しで直す。ただし初月はベースラインの取得を優先し、前倒しはしない。
- **初月**: ベースラインを取る月にする。
  - 即時対応の対象（セキュリティ、データ損失）以外のハーネス変更は止め、すべて仮説 Issue に積む。変更を続けると、数値が何の効果なのか分からなくなるため。
  - 実装は集計スクリプト1本と、上の手動チェックリストだけにする。月次 skill と Actions は、3か月後の見直しで必要と判断したときに作る。枠組み自体がハーネスいじりの新しい題材にならないようにするため。

## 7. 対象範囲と対象外

- 対象は、完了ゲートを持つ自分のリポジトリ。完了ゲートは既存の機械的チェック（lefthook の pre-push、CI）をそのまま使い、各 CLAUDE.md には「完了 = <コマンド> が通る」の1行だけを書く。
- 完了ゲートのないリポジトリ（playground 系など）は集計から外し、完了かどうかは人が判断する。月次見直しで一覧に出す。
- 他人が所有する OSS には適用しない。自分が AI を楽に使うために、他人のリポジトリを書き換えない。そこへの貢献は、キャリア軸の成果としてだけ数える。
- リポジトリごとの「良い・悪い」は定義しない。評価はこの枠組みの軸だけで行う。

## 8. 却下した案

- **リポジトリごとの良し悪しの定義**: OSS のつもりで作っているリポジトリに自分の物差しを当てるのは不適切。文章で条件を書くと、その判定をまたモデルに任せることになる。
- **介入率の数値目標（例: 月30%減）**: ハックできる。続けるとゼロ、つまり必要な介入までなくす方向に向かう。
- **仮説を Contextual Commits の本文に書く**: コミットメッセージに混ぜたくない。
- **仮説台帳をローカルの JSONL にする**: ログのように残すのはやりすぎ。Issue で足りる。
- **ops に置く**: ops はキャリアと学習に集中させる。ハーネスへのフィードバックは dotfiles の中で閉じる。
- **Claude による全件分類**: 使用量が大きい。サンプリングと軽量モデルで足りる。
- **月次の集計を Claude のスキャンで行う**: 使用量を消費し、毎回結果が変わる。集計はスクリプトで決定的に行う。
- **余った使用枠を使い切る**: 手段の目的化そのもの。
- **成果あたりの使用量（マージ PR あたりトークン）**: 「どれだけ使ったか」を評価しないという方針と矛盾する。`rate_limits` は PR 単位で取れず、`logs.db` にはサブエージェント分が入らないため、データ源もない。
- **使用量の算出のために save-transcript を拡張してサブエージェント分を含める**: 厳密さは不要。
- **安全なコマンドの許可ルールを自動で追加する**: AI が自分の権限を広げる経路になる。fail-closed の原則（`rules/security.md`）に反する。
- **最初から月次 skill と Actions を作る**: 枠組み自体が大きなハーネス作業になる。3か月の見直し後に判断する。
- **ガードファイルの差分から緩和を自動判定する**: 差分から緩和かどうかを機械的に判定できない。

## 9. 未決事項

作る前に確かめること:

- 手渡しが transcript にどう現れるか（拒否と区別して数えられるか）。
- 手戻り率の具体的な算出方法（マージ後の `fix` コミットをどの PR に紐づけるか、レビューの往復回数をどこから取るか）。
- 「計画の承認」を transcript から機械的に特定できるか。

実装:

- 集計スクリプトの置き場所と実装言語。
- ステータスラインから `rate_limits` と `cost` をローカル JSONL に追記する仕組み。初月はベースライン取得のためなので、変更停止の例外として入れる。
- ops のキャリア・プロダクト Issue キューの形（既存のラベルで足りるか）。

最初の仮説候補（初月は Issue に積むだけ）:

- 7日枠の残量表示を、残りが少ないときだけ出す形に変える。
- shguard が git で戻せる操作（例: `branch -d`）まで止めていることが、不要な介入の発生源になっていないか。

## 10. 事前検死

1年後にこの枠組みが失敗していたとしたら、最も可能性が高い理由は次のとおり。

- 大事な指標が取れていない。介入率だけがハックされ、直しているように見えて大事な問題が解消されない。あるいは、介入は下がったが安全性も下がっている。4節の見張り役で検出する。
- ハーネスは改善したのに、外に出せない自分の理解不足が積み上がる。3節の月次の理解確認で抑える。
- 枠組みを言語化しただけで、運用が続かない。4節の「月次見直しの2回連続の未実施」で検出する。
- 枠組みそのものが新しいハーネスいじりの題材になる。6節の「初月はスクリプト1本と手動チェックリストだけ」で抑える。
